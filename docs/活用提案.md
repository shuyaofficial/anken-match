# 「内容抽出」設計思想の活用提案

調査日 2026-07-05

対象: 内容抽出（Anken Match） — 案件メールをLLMで構造化抽出し、自社人材とスコアリングでマッチングするBYOK型SPA。データはIndexedDBにローカル完結、サーバ無し。

核となる思想: **非定型テキストの構造化 × 構造化データ同士のマッチング**。
このアプリの基盤要素は以下の4つ。応用例の実装規模はこれらの再利用度で見積もる。

- LLM抽出（自由記述→スキーマ準拠JSON）
- 正規化辞書（表記ゆれの吸収。例: "AWS"/"Amazon Web Services"→canonical名）
- スコアリング（必須/歓迎の充足率・加点・欠落抽出）
- IndexedDB（ローカル完結、サーバ不要）

## 1. 設計思想の応用例

各項目: 構造化対象と照合対象 / 業務上の価値 / 追加実装規模（小・中・大）。
規模の目安 — 小: スキーマとプロンプトの差し替えのみ数日規模。中: 新規の正規化辞書やスコアリング軸が必要、1〜2週間規模。大: 新規データソース連携やUI設計から必要、1か月以上規模。

1. **障害報告メール／インシデント記録 → 過去ナレッジ照合**
   - 構造化: 発生事象・影響範囲・原因カテゴリ・対処内容。照合先: 過去の障害ナレッジベース（同一事象パターン）
   - 価値: 一次対応者が「似た障害の過去解決策」に即到達。属人化した経験知の再利用
   - 追加実装規模: 中（障害特有の正規化辞書＝機器名・エラーコード表記ゆれの吸収が必要）

2. **研修受講履歴・自己申告スキル → 育成計画・アサイン候補選定**
   - 構造化: 受講研修名・取得資格・自己評価レベル。照合先: 案件要求スキル、または次のキャリアパス定義
   - 価値: 「このアプリ自体のEmployeeSkillモデル」を人材育成側に拡張し、案件だけでなく研修設計にも使う
   - 追加実装規模: 小（EmployeeSkill/スコアリングをほぼ流用可能）

3. **RFP／提案依頼書 → 過去提案・事例照合**
   - 構造化: 調達要件・予算感・技術要件・評価基準。照合先: 過去提案書アーカイブ、過去案件の成果サマリ
   - 価値: 提案書の初稿を「過去の類似提案の再利用」から始められる。提案工数の圧縮
   - 追加実装規模: 大（RFPは案件メールより長文・多様な様式で、抽出精度確保にプロンプト設計の作り込みが要る。過去提案書側のテキスト化・構造化も新規）

4. **求人票・スカウトメール → 自社求職者／候補者照合**（人材紹介・派遣業向け）
   - 構造化: 求人要件・条件面。照合先: 求職者プロフィール
   - 価値: 内容抽出のモデルをほぼそのまま転用可能。SES以外の人材紹介業態への横展開
   - 追加実装規模: 小（ドメイン語彙の正規化辞書を差し替える程度）

5. **契約書・見積書の条項 → 自社標準条項・過去契約照合**
   - 構造化: 契約条項（支払条件・解除条項・責任範囲等）。照合先: 自社標準テンプレ条項、リスク条項リスト
   - 価値: 非定型な契約書から「標準からの逸脱箇所」を自動抽出。法務レビューの一次スクリーニング
   - 追加実装規模: 大（条項単位の抽出粒度が細かく、誤抽出時の実害＝法的リスクが大きいため検証機構が要る）

6. **問い合わせメール・レビュー文 → FAQ／製品仕様照合**
   - 構造化: 問い合わせ内容・感情・製品カテゴリ。照合先: FAQデータベース、既知不具合リスト
   - 価値: 一次回答の下書き自動生成の前段階として、関連FAQへの自動ルーティング
   - 追加実装規模: 小〜中（FAQ側は既存データが構造化済みであることが多く、照合ロジックのみ追加）

7. **求人媒体の職務経歴書（レジュメ） → 案件要件照合の逆方向**
   - 構造化: 経歴書の職務内容・保有スキル・年数。照合先: 複数案件の要求スキル一覧
   - 価値: 「人から案件を探す」向き。現行の「案件から人を探す」の対称形で、UIとスコアリングの向きを反転するだけ
   - 追加実装規模: 小（MatchResultの入出力を入れ替える設計変更が中心）

8. **不動産・設備の点検報告書 → 修繕履歴・保守マニュアル照合**
   - 構造化: 点検箇所・劣化状況・緊急度。照合先: 過去修繕履歴、保守マニュアルの該当箇所
   - 価値: 非IT業種（不動産管理・設備保守）への思想の転用例。点検員の自由記述を構造化してナレッジに接続
   - 追加実装規模: 大（新規ドメインの正規化辞書をゼロから構築。専門用語・略称の辞書化コストが高い）

## 2. 既存サービス調査

SES業務管理・案件マッチングSaaS3件、タレントマネジメント1件、汎用CRM1件を調査。価格は2026-07-05時点の各社公開情報。

### 2-1. assign navi（アサインナビ）

- 概要: IT企業とフリーランスエンジニア・コンサルタントの案件・人材マッチングプラットフォーム。企業間・企業-フリーランス間のマッチングが中心
  出典: [assign navi](https://assign-navi.jp/)
- 価格帯: フリープラン（月60チケット、繰越不可）。ベーシック（初期110,000円/年330,000円/年1,000チケット）。ビジネス（初期110,000円/年660,000円/年3,000チケット）。プレミアム（初期110,000円/年1,320,000円/チケット無制限）。案件応募5チケット消費、フリーランス成約時に成約手数料（月単価帯により110,000〜220,000円）
  出典: [料金プラン | assign navi](https://assign-navi.jp/plan)
- 強み: 5,700社以上・9,300人以上のフリーランスが登録する大規模マッチングマーケットプレイス。社外の未知の人材・案件にリーチできる
  出典: [assign navi](https://assign-navi.jp/)
- このアプリとの違い: assign naviは「社外に開いたマーケットプレイス」であり相手探索そのものが価値。内容抽出は「自社内の受信メールと自社社員」という閉じたデータの照合に特化し、外部マーケットへのリーチは持たない

- 概要: 人材派遣・人材紹介業向けクラウド業務管理システム。求人管理・人材管理・マッチング・契約・勤怠・給与請求までを一気通貫でカバー
  出典: [MatchinGoodとは？ | アスピック](https://www.aspicjapan.org/asu/service/11575)

  出典: [料金プラン（紹介） | MatchinGood](https://www.matchingood.co.jp/price/shokai/)

  出典: [MatchinGoodとは？ | アスピック](https://www.aspicjapan.org/asu/service/11575)

  出典: [SESクラウドが累計導入社数1,000社突破 | PR TIMES](https://prtimes.jp/main/html/rd/p/000000016.000028237.html)

  出典: [料金｜カオナビ](https://www.kaonavi.jp/price/)
- 強み: 人材データの一元化・可視化・分析に強く、人事評価や配置シミュレーションなど人事戦略全体を支える。スキル定義を柔軟にカスタマイズ可能

  出典: [2026年最新Salesforce価格 | GENIEE's library](https://geniee.co.jp/media/crm/salesforce-pricing/)

  出典: [2026年最新Salesforce価格 | GENIEE's library](https://geniee.co.jp/media/crm/salesforce-pricing/)

## 3. 自作の優位性と限界

### 自作が現実的になった理由

- 非定型テキストの構造化（案件メールの自然文解析）が、以前は自然言語処理の専門実装が必要だったが、LLM API呼び出し1本＋プロンプト設計で代替可能になった
- BYOK方式（利用者自身のAPIキー）により、自社でLLM利用料を負担する必要がなく、開発側はインフラコストを持たない
- IndexedDBでのローカル完結により、サーバ・DB運用・認証基盤が不要。個人〜小規模開発でも本番品質のツールを保守できる

### 自社フォーマット・商流特有情報への適合性

- ExtractedProjectモデルに商流（エンド直・1次請け等）、面談回数、外国籍可否等の"notes"を最初から型として持てる。既存SaaSは汎用スキーマのためカスタムフィールド追加や設定変更が必要になりがち（assign navi・SESクラウドは業界標準フィールドは持つが、自社独自の商流表現や社内呼称までは前提にしていない）
- 正規化辞書を自社のスキル呼称・略称に合わせて自由にチューニングできる。汎用CRM（Salesforce等）では同等のことをカスタムオブジェクト設計から行う必要がある

### 一方でSaaSに劣る点

- マルチユーザー同時編集・権限管理（閲覧/編集権限の細分化）は現状スコープ外。IndexedDBはブラウザ単位でデータが閉じるため、複数営業担当での共有が前提のワークフローには向かない
- 監査ログ（誰がいつ何を変更したか）の仕組みがない。コンプライアンス要件がある組織では不足
- ベンダーサポート・SLA・障害対応体制がない。開発者本人が保守を止めれば継続性のリスクがある
- 他社との案件・人材情報の共有（assign navi・SESクラウドが持つ社外マッチング機能）は範囲外

### 自作で十分な規模の目安

- 人数: 営業・コーディネーター1〜3名程度。同時編集の必要がない規模
- 案件量: 月間数十〜200通程度のメール処理まではLLM抽出＋ローカルDBで十分に回る。数千通/月やマルチ拠点での共有が必要になった時点でSaaS化・サーバ移行の検討ライン
- 上記を超える規模（人数増・複数拠点・監査要件）になった場合、MatchinGoodやSESクラウドのような業務基盤SaaSへの移行、または自作をサーバ型に拡張する判断が必要
